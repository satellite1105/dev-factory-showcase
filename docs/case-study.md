> 実例1〜3は、この基盤とこのリポジトリ自身の非公開の記録を確認して要約したものです。案件の名称・内容・数値は含めません。

## この文書の読み方

前半では、基盤とこのリポジトリ自身について残された記録から、課題と対応、確認できた範囲を紹介します。検証ステータスの参照は、それぞれの仕組みの根拠と限界に対応します。過去の対象版での成功を、現在版の全経路の成功とは扱いません。

後半では、単語頻度カウンタの架空の依頼を使って、要件から納品までの進め方を説明します。実物のコード・テストの案内は [サンプルの README](../examples/dummy-project/README.md)、実績と今回の確認状況は [検証ステータス](verification-status.md) を参照してください。架空の採点と実際の独立レビューは別の記録です。

## 実例1: このリポジトリ自身の作成と更新

**課題**: 基盤を紹介する文書には、説明用の例と実際の開発結果が混在しやすい問題があります。初回作成のレビューでは、委譲件数とフォールバックの説明が作業記録に合っていない箇所も見つかりました。

**設計判断**: 実績を書く際は、委譲した事実、実装を完了した担当、検査とレビューの結果を分けて照合します。説明用の物語を、実行の証拠として数えない方針です。

**仕組み**: 初回作成では編集するファイルが重ならないように分担し、リーダー(オーケストレーター)が成果を統合して再検査しました。独立レビューの指摘を受け、委譲記録を別経路の集計とも突き合わせ、件数と引き継ぎの説明を直しました。今回の更新は「調査 → 差分表 → 更新 → 検査 → 独立レビュー → 公開前の承認」の順に進める手順です。ここでは今回の各工程の成功は認定しません。

**確認結果**: 2026-10-21 の初回作成版には、企画・設計から実装、検査、独立レビュー、指摘修正後の再確認までの記録があります。対象は当時の作成作業です。(検証ステータス: 実機検証済み / P08)

wordfreq の実装では、委譲文の参照先不足により Codex が通常の失敗となり、Claude の実装担当へ引き継いで完了しました。この切替は当該タスクだけに適用されました。(検証ステータス: 実機検証済み / V03)

**限界**: 初回作成の完了は今回の更新版の完了証拠にはなりません。また、この作成作業ではインフラ系失敗の連続による circuit breaker は発動しておらず、通常の失敗後の引き継ぎと区別する必要があります。工数や費用の削減効果は未測定です。

## 実例2: 完了報告の欠落を失敗と数えた誤判定と、その修正

**課題**: 運用中の長時間タスクで、処理が正常に終わり成果物を採用できたにもかかわらず、完了報告が届かなかったことを失敗として計上していました。そのため、障害時の切替が誤って働きました。

**設計判断**: 報告が届いたかどうかと、元の実行が終了したかどうかを分けます。完了報告が欠けた結果は「結果未確定」として保留し、報告の欠落だけで失敗を増やさない方針に改めました。

**仕組み**: リーダーは判定ツールで元の実行の状態を調べ、終了と成果物を照合してから、重複させずに結果を確定します。実行中や状態不明なら後続の実装を開始せず、終了済みと確認できた場合に成果の採用または引き継ぎを判断します。別の作業の終了によって共有の実行基盤を止めない保護も、この判断を支えます。

**確認結果**: 改訂時には過去の実行記録を再生し、単体テストと合わせて、報告欠落を保留し誤計上を解消する処理を確かめました。(検証ステータス: 一部検証 / V25)

隔離した試験用環境では、中断後の再開で、終了後の採用・引き継ぎと実行中の待機を確認しています。(検証ステータス: 一部検証 / V26)

共有の実行基盤については、当時の Mac 上で、他の作業の終了後も処理を継続できる経路と、終了する作業自身の処理を識別して中断する経路の記録があります。(検証ステータス: 実機検証済み / V27)

**限界**: 改訂後に外側の待機時間を超える長時間処理を、新たに実機で再現した記録はありません。判定ツールは状態の確認を助けますが、後続担当の起動を機械的に止めるものではなく、結果の確定と開始の判断にはリーダーの手順が必要です。元の実行に由来する背景処理をすべて観測・終了できる保証もありません。

## 実例3: 保護機構の更新を、隔離テストと独立レビューの合格で反映する

**課題**: 操作を制限する保護機構も、変更する際に誤りを持ち込む可能性があります。実装担当の自己申告だけでは、評価した版と実際に反映する版の一致を確かめられません。

**設計判断**: 作業範囲を守るよう依頼するだけでなく、隔離したテストと独立レビューを、反映を進めるための条件にします。評価を対象版へ結び付け、異なる版の合格を流用しない構成です。

**仕組み**: 保護機構の変更は専用の経路で扱い、実装とは別の担当が評価します。隔離した複製で所定のテストを行い、レビュー結果とテスト対象、反映する内容が一致することを照合してから反映します。これは、担当への指示に加え、機械的な検査を反映の条件にする例です。

**確認結果**: 2026-10-28 の保守版には、独立レビューを経て隔離テストと反映を完了した記録があります。評価対象のファイルは現在の内容とも一致します。確認できるのは、記録された正常な評価・検証・反映の経路です。(検証ステータス: 実機検証済み / V30)

**限界**: 根拠は上記の成功経路に限られ、中断や時間超過のすべての分岐を確認したものではありません。レビュー依頼の書き方が評価を誘導する可能性を、機械的に排除することもできません。

## 説明用の再構成: 単語頻度カウンタを依頼から納品まで

以下の進行、CSV 不具合と修正、採点は架空です。実物のコード・テストの作成事実とは分けて読み進めてください。

### 依頼と要件

「文章中の語を数え、ファイルと標準入力から読み、上位の語を text・csv・json で出したい」という依頼を想定します。[spec](../examples/dummy-project/spec.md) のように機能と確認条件を対応させます。

| 必須要件 | 確認する条件 |
| --- | --- |
| [F1] 標準入力・UTF-8 ファイルを読み、複数ファイルを合算する | [S1] 入力経路ごとに集計を確認する |
| [F2] 語を数え、既定で大小文字をまとめる | [S1] 語の扱いを確認する |
| [F3] 頻度の降順、同数なら語の昇順にし、表示数を指定できる | [S1] 並び順と表示数を確認する |
| [F4] 各形式で出力し、空入力でも CSV 見出しを残す | [S2] 形式ごとの出力と空入力を確認する |
| [F5] 除外語ファイルを読み、大小文字を区別せず除外する | [S3] 除外と入力エラーを確認する |

[S4] には README の使用例、テスト成功、レビュー合格を置きます。Python の標準ライブラリだけを使い、日本語の形態素解析は行わず、入力全体をメモリへ読むという前提も、この架空の要件に含めます。

### 設計と分担

リーダーが依頼を受け、planner(企画)が要件を整理し、architect(設計)がタスクを分ける想定です。まず集計・整形の関数を確定し、その後の担当が同じファイルを編集しないようにします。

| 順序 | 想定する担当とファイル |
| --- | --- |
| 先行 | 集計・整形: `wordfreq/core.py`、`wordfreq/__init__.py` |
| 並列 | CLI: `wordfreq/__main__.py` / 集計テスト: `tests/test_core.py` |
| 後続 | CLI 統合テスト: `tests/__init__.py`、`tests/test_cli.py` |
| 最後 | 使い方、要件、状態、レビューの文書 |

これは分担の説明例です。各担当へ編集範囲とテスト方法を伝えることと、書き込みを機械的に隔離することは別です。実際の作業範囲制限の確認状況は限定されています。(検証ステータス: 一部検証 / V17)

### 実装とテスト

想定する進行では、入力・集計・整形を実装し、通常入力に加えて空入力や異常系をテストします。実物の [集計・整形コード](../examples/dummy-project/wordfreq/core.py) と [CLI](../examples/dummy-project/wordfreq/__main__.py)、それぞれのテストはリポジトリ内で確認できます。

実物のテスト群は、リポジトリのルートから実行できます。

```sh
python3 -m unittest discover -s examples/dummy-project/tests -t examples/dummy-project
```

初回作成時に加えて、今回の公開前の最終候補(2026-11)でも再実行し、全件成功・skip なしを確認しています。範囲は同梱サンプルのテストだけで、基盤全体の動作確認ではありません。現在の分類は [検証ステータス](verification-status.md) にまとめています。(検証ステータス: 実機検証済み / P03)

通常の失敗なら当該タスクを引き継ぎ、インフラ系の失敗が同一フェーズで連続した場合は circuit breaker で残作業の切替を判断する設計です。改訂後の計数処理には再生試験がありますが、その分類に基づく実運用の発動は未確認です。(検証ステータス: 一部検証 / V04)

### レビューと修正(再構成)

[REVIEW](../examples/dummy-project/REVIEW.md) の架空の採点は、要件、テスト・検証、コード品質、文書に、それぞれ 0.4 / 0.3 / 0.2 / 0.1 の重みを付ける例です。

| 回 | 要件 | テスト・検証 | コード品質 | 文書 | 加重平均 | passed |
| --- | --- | --- | --- | --- | --- | --- |
| 1回目(再構成) | 0.8 | 0.7 | 0.8 | 0.8 | 0.77 | false |
| 2回目(再構成) | 0.9 | 0.9 | 0.85 | 0.8 | 0.88 | true |

初回は、空入力で CSV 見出しが消えると仮定し、finding を `CSV-EMPTY`、severity を `critical` とします。[F4]・[S2] の必須条件の未達は重大な誤りとして `critical_errors` に記録し、総合点にかかわらず不合格とします。空入力でも `word,count` と改行を返すように直し、回帰テストと他形式の確認を行う想定です。実物のコードはすでに見出しを返すため、この修正前の不具合を現行コードで再現することはできません。

実際の基盤では、点数に加え、`passed: true`、空の `critical_errors`、計算との一致、必須要件・完了条件・重大な制約に未達がないことを合わせて判定します。独立レビューの実績は 2026-10-21 の初回作成版に限定して参照します。(検証ステータス: 実機検証済み / V06)

再構成した2回目では、指摘を修正し再現結果を確認できたと仮定し、0.88 で合格とします。レビューは最大3回とし、未達のまま上限に達したら `blocked` として判断を求める設計です。実際には修正後の再レビューの記録がありますが、上限未達で停止する経路は未確認です。(検証ステータス: 一部検証 / V07)

### 納品と完了判定(再構成)

架空の [PROJECT_STATE](../examples/dummy-project/PROJECT_STATE.md) では、GOAL_CONTRACT に完了条件と検証方法を置きます。completion gate で条件の達成、検証成功、対象版の最新の証拠、レビュー合格、重大な制約違反や停止条件がないことを確かめ、揃った場合だけ `completed` にする想定です。このサンプルの状態や証拠は架空です。基盤の完了手順には当時の運用記録がある一方、条件未達による停止の実例は未確認です。(検証ステータス: 一部検証 / V11)

納品時には CLI・テスト・説明文書とともに、実行方法、前提、確認結果、残る制約を伝えます。この物語の最終点 0.88 は説明用であり、日本語の形態素解析を行わないことや、入力をメモリへ読むことも、想定した要件の制約として報告します。
