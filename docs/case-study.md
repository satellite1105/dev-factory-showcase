# 開発事例: 単語頻度カウンタを依頼から納品まで

> 記述時点: 2026-10。内容は非公開の内部概要資料(v2 系)から概念レベルで書き下ろしたもので、内部仕様は今後変わる可能性があります。
> 依頼から納品までの進行、CSV 不具合の修正履歴、レビュー点数の 0.77 → 0.88 は説明用の再構成です。独立した実レビューや実行ログを示すものではありません。
> wordfreq のコードと37件のテストは、このリポジトリを作った実行中の実物です。実際の実装は Codex への委譲が通常の失敗となり、Claude の coder(実装)へフォールバックして行われました。

実物の作成経緯と使い方は [サンプルの README](../examples/dummy-project/README.md)、再構成した採点は [REVIEW](../examples/dummy-project/REVIEW.md) で確認できます。このリポジトリ全体の実際の実行実績(委譲の内訳と、実際のレビュー結果)は検証ステータスの P08 にまとめています。以下の架空の点数は P08 の実績とは別のものです。(検証ステータス: 実機検証済み / P08)

## 依頼(架空)

「文章に含まれる語の回数を数えたい。ファイルと標準入力に対応し、上位の語を text・csv・json で出力する CLI を作ってほしい」という依頼を想定します。GUI やネットワーク連携は求めず、ローカルで結果を確認する小さな道具を対象にします。

この例では、リーダー(オーケストレーター)が依頼を受け付け、planner(企画)が要件を整理し、architect(設計)が担当を分けます。その後に実装、統合・デバッグ、reviewer(検証)による評価、納品へ進む構成です。基盤には小規模な全フェーズ完走の確認記録がありますが、この物語自体はその記録ではありません。(検証ステータス: 実機検証済み / V01)

## spec: 欲しい機能を確認できる条件へ変える

[spec](../examples/dummy-project/spec.md) は、機能を `[F]`、成功条件を `[S]` の ID で結び付ける例です。「CSV に対応する」という要望を、空入力でも確認できる条件まで具体化します。

| 必須要件 | 成功条件との対応 |
| --- | --- |
| [F1] 標準入力・UTF-8 ファイルを読み、複数ファイルは合算する | [S1] 入力経路ごとの集計を確かめる |
| [F2] 語を数え、既定で大小文字をまとめる | [S1] 大小文字や語の扱いを確かめる |
| [F3] 頻度の降順、同数なら語の昇順。`-n` は1以上 | [S1] 並び順と表示数を確かめる |
| [F4] text・csv・json を出力し、空入力でも CSV 見出しを残す | [S2] 各形式と空入力の出力を確かめる |
| [F5] 除外語ファイルを読み、大文字小文字を区別せず除外する | [S3] 除外語と入力エラー・不正な表示数を確かめる |

[S4] は README の使用例、全テスト、レビュー合格をつなぐ条件です。前提として Python の標準ライブラリだけを使い、日本語は連続した文字のまとまりとして扱います。形態素解析と、入力全体をメモリに載せず処理する方式は対象外とします。これらはサンプルの架空の要件設定です。

## 設計とタスク分割

架空の設計では、まず集計・整形を担う `wordfreq/core.py` と公開する関数を確定します。そこから入力処理、集計処理のテスト、CLI のテストへ依存関係を分けます。共有部分を先に揃え、並列に進める担当同士で編集先が重ならないようにする考え方です。(検証ステータス: 実機検証済み / V05)

以下は分割の説明例であり、実際の担当履歴ではありません。パスはサンプル内を基準にしています。

| 順序 | 担当タスク | 編集するファイル | 前提 |
| --- | --- | --- | --- |
| 先行 | 集計・整形と公開関数の確定 | `wordfreq/core.py`、`wordfreq/__init__.py` | spec の要件を確認する |
| 並列A | CLI の入力・引数処理 | `wordfreq/__main__.py` | 先行タスクの関数を使う |
| 並列B | 集計・整形のテスト | `tests/test_core.py` | 先行タスクの関数を使う |
| 後続 | CLI の統合テスト | `tests/__init__.py`、`tests/test_cli.py` | 並列Aの CLI が揃っている |
| 最後 | 使い方と要件・状態・レビューの文書化 | `README.md`、`spec.md`、`PROJECT_STATE.md`、`REVIEW.md` | 実物と検証結果を照合する |

各担当には対象の案件、担当ファイル、要件、実行するテストを渡し、他のファイルを変更しないよう指定します。この範囲指定は指示としての境界であり、Codex 側の書き込みを技術的にすべて遮断する保証ではありません。(検証ステータス: 一部検証 / V17)

## 実装とテスト

### 実際に起きたフォールバック

wordfreq の実装タスクは、まず Codex に渡されました。参照先の指定が漏れていたため通常の失敗となり、同じタスクを Claude の coder へ引き継いで実装しました。これはこのリポジトリを作った実行で起きた実例です。失敗したタスクだけをフォールバックし、別の独立したタスクでは再び Codex を優先する方針に沿っています。(検証ステータス: 実機検証済み / V03)

通常の失敗は circuit breaker の連続失敗に数えません。circuit breaker が扱うのはインフラ系の失敗で、同一フェーズ内で2回続いた場合に残りの作業を Claude に回します。今回の実装タスクの通常の失敗を、その発動実績としては扱いません。(検証ステータス: 実機検証済み / V04)

### 実物で確かめられること

[集計・整形のコード](../examples/dummy-project/wordfreq/core.py) は語の抽出、集計、並べ替え、出力形式、除外語を扱い、[CLI](../examples/dummy-project/wordfreq/__main__.py) は入力と引数を扱います。[集計側のテスト](../examples/dummy-project/tests/test_core.py) と [CLI 側のテスト](../examples/dummy-project/tests/test_cli.py) には空入力や異常系も含まれます。サンプルの README と検証ステータス表には、37件を実行して `OK` となった実測結果があります。この件数は架空のレビュー点数から求めたものではありません。(検証ステータス: 実機検証済み / P03)

リポジトリのルートで、次のコマンドから同じテスト群を実行できます。

```sh
python3 -m unittest discover -s examples/dummy-project/tests -t examples/dummy-project
```

ここからの「不合格 → 修正 → 合格」は、品質ゲートを説明するための再構成です。現行コードの不具合履歴や、上の37件のテストを実行した履歴とは分けて読み進めてください。

## レビュー: 1回目の不合格から2回目の合格へ

### 1回目: 0.77、不合格という例

reviewer は要件、テスト・検証、コードの品質、文書をそれぞれ採点し、順に 0.4 / 0.3 / 0.2 / 0.1 の重みで総合点を計算します。合格には 0.85 以上だけでなく、`passed: true`、空の `critical_errors`、加重平均を小数第2位に丸めた値との一致、必須要件・完了条件・重大な制約に未達がないことが必要です。(検証ステータス: 実機検証済み / V06)

[REVIEW](../examples/dummy-project/REVIEW.md) の架空の修正前の版 `example-before` は、次の採点で不合格になります。

| 回 | 要件 | テスト・検証 | コードの品質 | 文書 | 加重平均 | passed |
| --- | --- | --- | --- | --- | --- | --- |
| 1回目(再構成) | 0.8 | 0.7 | 0.8 | 0.8 | 0.77 | false |
| 2回目(再構成) | 0.9 | 0.9 | 0.85 | 0.8 | 0.88 | true |

```text
1回目: 0.8 × 0.4 + 0.7 × 0.3 + 0.8 × 0.2 + 0.8 × 0.1
      = 0.32 + 0.21 + 0.16 + 0.08 = 0.77
2回目: 0.9 × 0.4 + 0.9 × 0.3 + 0.85 × 0.2 + 0.8 × 0.1
      = 0.36 + 0.27 + 0.17 + 0.08 = 0.88
```

### finding の再現と修正(再構成)

初回の finding は `CSV-EMPTY`、severity は `major` とします。[F4]・[S2] に対し、空入力で CSV の見出しが消えると仮定した指摘です。再現手順はサンプル内で次を実行することです。

```sh
cd examples/dummy-project
printf '' | python3 -m wordfreq --format csv
```

| 照合項目 | この例での内容 |
| --- | --- |
| 期待する出力 | `word,count` と改行 |
| 修正前の想定 | 標準出力が空になる |
| 原因の想定 | データ行がある場合だけ見出しを出していた |
| 修正範囲・方針 | `format_rows` で行の有無にかかわらず CSV 見出しを出し、空入力の回帰テストを確認する |
| 修正後の確認 | 見出しが残り、通常入力の CSV と他形式のテストも成功する |

この不具合と修正は架空です。現行の `format_rows([], "csv")` はすでに見出しを返し、空入力を確認するテストもあります。上のコマンドを現行コードで実行しても、修正前の空出力を再現することにはなりません。

指摘の修正では、リーダーが再現手順・原因・範囲・方針を渡し、Codex を優先して作業を委ねます。debugger(デバッグ)へのフォールバックはその作業が失敗した場合の選択肢です。reviewer は自ら直さず、修正前後の再現結果を受け取って評価します。(検証ステータス: 実機検証済み / V06)

### 2回目: 0.88、合格という例

架空の修正後の版 `example-after` では、指摘への対応、再現確認、影響するテストと使用例の確認が済んだと置きます。総合点は 0.88、`passed: true`、`critical_errors` と未解決の finding は空で、必須要件の未達もないため合格とする例です。この点数は実際のリポジトリ全体に対する品質評価ではありません。

再レビューへは「指摘 → 対応 → 修正後の再現結果」を引き継ぎます。レビューは最大3回とし、上限でも合格条件が揃わなければ `blocked` にして必要な判断を報告する設計です。再レビューの実績はありますが、上限未達で `blocked` になる経路の検証記録はありません。(検証ステータス: 一部検証 / V07)

## 納品: completion gate を確認してから完了にする

再構成した [PROJECT_STATE](../examples/dummy-project/PROJECT_STATE.md) では、GOAL_CONTRACT に完了条件と検証方法をまとめ、`example-after` と2回目のレビューを対応させています。completion gate では、[S1]〜[S4] の達成、検証の実行と成功、対象の版に対応する最新の証拠、レビュー合格、重大な制約違反がないこと、停止条件に当たらないことを照合し、すべて揃った場合だけ `completed` にします。この例の状態と証拠は架空で、実案件の完了証拠には使えません。基盤の gate 自体も設計段階の分類です。(検証ステータス: 設計済み(未検証) / V11)

この物語の納品物は CLI、テスト、使い方、要件・状態・レビューの説明文書です。納品報告には実行方法、前提、再構成した最終点 0.88、残る制約を添える想定です。日本語を形態素に分けないことと、入力全体をメモリに読むことは、この例の要件範囲に含めた制約として伝えます。

## 品質ゲートがどこで働いたか

- **実装・統合時**: 入力経路、集計、出力形式、空入力、異常系をテストします。実物の37件の確認結果は P03 に限定されます。(検証ステータス: 実機検証済み / P03)
- **初回レビュー時**: 再構成した例では 0.77 と [F4]・[S2] の未達により不合格とします。点数と必須条件を合わせて判定する仕組みです。(検証ステータス: 実機検証済み / V06)
- **修正後の再レビュー時**: 指摘と再現結果を対応させ、再構成した例では2回目の 0.88 で合格します。上限未達時の停止経路は未確認です。(検証ステータス: 一部検証 / V07)
- **納品前**: レビュー点数に加え、完了条件・最新の証拠・制約・停止条件を completion gate で照合する設計です。(検証ステータス: 設計済み(未検証) / V11)
