# 委譲と状態管理

> 記述時点: 2026-11。基盤の現在のファイルと非公開の作業記録を確認し、公開向けに概念レベルで書き下ろしたものです。内部仕様は今後変わる可能性があります。

## Codex-first の方針

判断と実作業がリーダーに集中するのを避けるため、Claude は企画・設計の判断、統合、レビューを担い、実装とデバッグはまず Codex に委ねます。大量の読解、広範囲の検索、集計・照合、データ変換、処理用スクリプトの作成も対象です。2026-10-21 の初回作成版には委譲と受領を確認した記録があります。確認範囲は個別の実装例であり、作業全種類への適合や Claude 使用量の削減効果は測定していません。(検証ステータス: 実機検証済み / V02)

事前の動作確認だけが失敗したことで実作業まで別担当へ移さないよう、事前確認を全タスク共通の開始条件にはしません。対象タスクを実際に委譲し、その結果を確認する手順として定めています。この方針と、事前確認の有無による効果を比較できたことは別です。

## 委譲の単位と渡す情報

並行する作業が同じファイルを変更すると、統合時に衝突しやすくなります。そこで、共通の型や接続仕様を先に確定し、担当ファイルが重ならない単位へ分解します。各担当には目的、必要な要件と設計、変更対象、テスト方法、報告形式を渡します。2026-10-21 の初回作成版には、この分担で成果を受領して統合した記録があります。担当分離と統合の事例であり、並列化による速度差は未測定です。(検証ステータス: 実機検証済み / V05)

## 実装レーンの事前分類

作業の条件に応じた実行構成を使うため、リーダーが委譲前に「標準・効率重視・難所向け」の3つの実装レーンから選びます。これは現行の分類手順として実装・運用しており、判断に迷うときは標準を選びます。Codex 自身がモデルを選択したり、自動で上位へ切り替えたりする運用ではありません。2026-10-10 の当時版では指定の伝達と受領を確認していますが、現在の全レーンの動作は未確認で、分類の妥当性、速度・費用への効果は未測定です。(検証ステータス: 一部検証 / V22)

## 結果の受領と実行の終了確認

報告が戻っても元の処理が続いていれば、別担当への引き継ぎで書き込みが重なります。委譲前に依頼ごとの識別子と変更前の状態を記録し、受領時と再開時には判定ツールで元の実行の状態を照合します。実行中または状態不明なら、リーダーは同じ担当ファイルへの引き継ぎや依頼の出し直しを保留します。終了済み、または未起動と確認できてから次の操作を判断します。(検証ステータス: 一部検証 / V26)

2026-10-26〜27 の隔離試験と 2026-10-31 の当時版の運用には、待機や終了確認後の引き継ぎの記録があります。状態の判定はツールが行いますが、別担当を始めないことはリーダーが守る手順です。起動を機械的に止める機能ではなく、元の実行が残した背景処理を観測できない場合もあります。委譲から受領までの構成は[全体構成](architecture.md)で示します。(検証ステータス: 一部検証 / V26)

## 失敗の分類とタスク単位のフォールバック

完了報告の不足を実行基盤の故障と取り違えないよう、結果を次のように分けます。(検証ステータス: 一部検証 / V25)

- 結果未確定: 完了報告が欠け、成否をまだ判断できない結果。報告が空の場合や待機の時間を超えた場合も、それだけで失敗とはしません。
- 通常の失敗: 実行できたものの、成果物や報告に不足がある結果。テスト未実行、テスト不合格、必要な報告形式を満たさない場合などです。
- インフラ系の失敗: 呼び出し、接続、認証、実行環境などの問題で、実行が成立しなかったと確認できる結果です。

結果未確定は受領時に成功・失敗へ数えません。元の実行が終わったことを確認し、成果物と担当テストを調べてから、成功・通常の失敗・インフラ系の失敗のいずれかへ確定し、一度だけ記録します。経過時間だけでは確定しません。2026-10-29 の改訂版には過去データの再生と単体テストの記録がありますが、改訂後の長時間実行を新たに実機で再現した記録はありません。確定と記録はリーダーの手順を含み、永続的な台帳が重複計上を自動で防ぐ保証はありません。(検証ステータス: 一部検証 / V25)

失敗が確定したら、元の実行の終了確認を経て、そのタスクまたはデバッグのラウンドだけを Claude の実装担当・デバッグ担当へ引き継ぎます。要件と完了条件を変えず、既存の変更と確認できた到達点を渡し、実行者と切り替え理由を記録します。通常の失敗であれば、次の独立したタスクは再び Codex から始めます。2026-10-21 の初回作成版と 2026-10-31 の基盤改修版に引き継ぎの記録がありますが、想定する故障すべての試験ではありません。(検証ステータス: 実機検証済み / V03)

## circuit breaker

実行基盤の障害が続く工程で委譲を繰り返さないため、実装とデバッグのフェーズを分けてインフラ系の連続失敗を数えます。同一フェーズで2回続いたら、そのフェーズの残作業を Claude へ切り替えます。発動前は成功または通常の失敗で連続数を戻します。通常の失敗自体は計上せず、結果未確定も確定するまでは計数を変えません。発動後は成功などがあっても状態を戻さず、同じフェーズの残りでは切り替えを維持します。別フェーズでは別に管理します。(検証ステータス: 一部検証 / V04)

計数の計算はツールにありますが、フェーズの管理、記録、実際の切り替えはリーダーの手順です。2026-09-13 の旧方式の発動記録と、2026-10-29 の改訂版の再生・計算試験は区別します。旧方式には後に誤分類と分かった発動例もあり、改訂後の分類による実運用での発動は未確認です。(検証ステータス: 一部検証 / V04)

## 共有の実行基盤の保護

ある作業を終えたことで、別の作業まで止めないようにします。共有の実行基盤は、他の接続や処理、実行中または状態不明の処理が残る間は停止を拒みます。一方、終了する作業自身の処理は、記録との対応を確認して中断の対象にします。2026-10-31 の Mac 上では、他の作業の終了後も実行が続く経路と、自分の処理を中断する経路を確認しています。最終確認版は現在のファイルと一致します。(検証ステータス: 実機検証済み / V27)

この確認は当時の Mac の継続・中断経路に限ります。途中で修正された版も区別して扱い、中断指示を送った厳密な時刻や全プロセスの終了まで保証するものではありません。実行基盤全体のテストには既知の失敗も残っています。(検証ステータス: 実機検証済み / V27)

## 作業範囲の制限

担当外の変更を避けるため、案件と担当ファイルの境界を指示し、委譲前に範囲宣言の事前検査を行います。作業後は変更前後の比較で範囲外の変更や検査できなかった部分を調べます。2026-10-26 の隔離試験には宣言不足を拒否した記録があります。開始前の検査と事後の検出は機械的ですが、通常経路で個々の書き込みを許可ファイルだけに隔離する機能ではありません。検出は防止とは異なり、比較による削除の検出にも限界があります。(検証ステータス: 一部検証 / V17)

基盤の共有領域にも、直接編集と委譲の両方に承認の境界を設けます。2026-10-07 の旧構成の境界検査と、2026-10-28 の保守版のテスト・配置照合には記録があります。現在版で実際の書き込みを試す境界検査は再実施しておらず、ハードリンクを通じた変更にも課題が残ります。(検証ステータス: 一部検証 / V15)

## 事前承認と隔離実行

対象を限定した変更を追加確認なしで進める場合には、通常の委譲とは別に承認・隔離経路を使います。事前承認の発行時に本人の確認を経て、作業範囲、期限、回数を固定し、実行時にも条件を照合します。2026-10-16〜24 の当時版には発行と条件外の拒否の記録があります。現在版の全条件を再試験したものではなく、承認内容の妥当性には人の判断も必要です。(検証ステータス: 一部検証 / V18)

承認された変更は隔離した複製で作り、承認範囲との照合後に作業対象へ反映します。2026-10-16〜24 の当時版で隔離実行と反映を確認しています。隔離の対象は実装担当側のツールであり、中継部分と実行器は信頼する前提です。実行環境の更新後に全経路を再確認したわけではありません。(検証ステータス: 一部検証 / V28)

反映中の中断に備え、反映の記録から変更前または変更後の整合した状態へ回復する仕組みもあります。2026-10-24 には試験用環境で障害を入れて回復を確認しました。この試験は本番の入口を通らず、本人の確認や操作前の検査を含む全体の証明ではありません。回復不能な状態や残った排他制御には人の対応が必要です。(検証ステータス: 一部検証 / V29)

## 保護機構の更新

保護機構自体の変更が未評価のまま通常作業へ混ざらないよう、未評価の変更が残る間は検証と反映を専用の経路へ回します。独立レビューと隔離テストを条件に、評価した対象版と反映内容を照合します。2026-10-28 の保守版には正常な評価・検証・反映を完了した記録があり、対象ファイルは現在の内容と一致します。確認範囲はその成功経路で、中断や時間超過の全分岐、レビュー内容の正しさまで機械処理だけで保証するものではありません。(検証ステータス: 実機検証済み / V30)

## 人の確認が必要な操作

削除、履歴の強制更新、本番への変更、外部公開、大きな課金、秘密情報の出力は人の判断へ戻す運用です。利用者が個別に確認を求めた操作も含みます。事前承認されたファイル変更は外部公開の許可を意味しません。特定の操作を拒否する実装や過去の制限の記録はありますが、現在版で対象操作すべての承認動作を確認したわけではなく、公開経路を一律に遮断する保証もありません。(検証ステータス: 一部検証 / V19)

## PROJECT_STATE

会話から離れても続きの作業を判断できるよう、PROJECT_STATE に依頼原文、承認済みの変更、GOAL_CONTRACT、工程の進捗、問題と対応、デバッグ・レビューの試行状況、実行者と切り替え理由、検証結果、残課題、次の操作を集約します。必要に応じて学習記録や自動再開に使う情報も残します。2026-10-26〜27 の再開模擬試験と 2026-11-08 の模擬保存には記録がありますが、保存できたことだけを再開成功とはしません。(検証ステータス: 一部検証 / V10)

```markdown
# PROJECT_STATE: sample-project
案件: sample-project
status: in_progress
最終更新: 架空の作業日

## 依頼原文
短い文章の単語を数える道具を作る。
## 承認済みの変更
なし。
## GOAL_CONTRACT
objective: 単語数を表示できる道具
done_when: 合意した入力例で期待値と一致する
verification: 設計に記載したテストを実行する
constraints: 外部への送信を行わない
allowed_files: sample-project の実装とテスト
budget: 既存のやり直し上限に従う
blocked_stop_condition: 上限内で解決できず判断が必要
last_verified_evidence: 未検証

## 実行者

## 検証結果

## 再開手順
```

## GOAL_CONTRACT と completion gate

完了の意味が進行中に曖昧にならないよう、GOAL_CONTRACT に目的、確かめられる完了条件、検証手段、制約、変更範囲、既存のやり直し上限、判断を求めて止める条件、最後に確認した証拠をまとめます。planner が要件を整理し、architect が検証方法などを具体化し、リーダーが状態記録へ集約します。証拠は対象の版へ結び付け、未確認なら未検証と記します。同じエラーが続く場合の方針変更は試行の戦略であり、それ自体を停止条件にはしません。(検証ステータス: 一部検証 / V11)

completion gate では、完了条件、検証成功、対象版に対応する最新の証拠、独立レビューの合格を照合し、必須事項の未達、重大な制約違反、停止条件への該当がないことを求めます。満たせない場合は `completed` とせず、`blocked` として最良の成果、最終スコア、未達事項、必要な判断を残します。通常の判定はリーダーと reviewer の確認手順であり、完了の記入を自動で禁止する汎用機能ではありません。2026-10-21 の初回作成版には証拠を保存し独立レビュー後に完了した記録がありますが、条件未達から `blocked` にした実例は未確認です。(検証ステータス: 一部検証 / V11)

## 作業区切りの保存と中断からの再開

区切りでは進捗、実行者、検証した対象版と証拠、次の操作を保存し、保存後に読み直します。未受領の結果、実行中または状態不明の処理、未確定の承認作業が残る間は、再開に備えた区切りの準備が整ったとは扱いません。2026-11-08 の記録は模擬保存と再開先の記載までで、実際に会話を整理した後の復元や、現行手順の全条件の確認ではありません。(検証ステータス: 一部検証 / V10)

再開時は `in_progress` の案件の状態記録と成果物を読み、完了済みの作業を繰り返さず、未受領の結果と元の実行の状態も確かめます。実行者と circuit breaker の状態を引き継ぎ、同じフェーズで発動済みなら残りは Claude が担います。古い記録の契約欄は既存の要件と設計から補い、`blocked` では理由と人の判断待ちを保持します。2026-10-26〜27 の隔離試験では採用・引き継ぎ・待機を分けましたが、現在の再開手順全体の実証ではありません。(検証ステータス: 一部検証 / V10)

## 監督付き自動再開

明示して開始する無人実行には、実行中だけ動く任意の監督プロセスを用意しています。子プロセスが異常終了した場合に、状態を読めること、`in_progress` であること、保存した実行情報が一致すること、想定外の変更や承認待ちがないことなどをすべて照合します。同じ作業区切りでの再起動は最大2回とし、同じセッション、次に状態記録を使う新しいセッションの順に試します。現在版で異常終了から実際に再起動する経路は未確認です。(検証ステータス: 一部検証 / V12)

正常終了、利用者による中断や終了シグナル、人の判断待ち、`blocked` または `completed`、状態の不明・破損、予想外の変更、Codex の実行中・状態不明、ループの検知では再起動しません。利用制限で子プロセスが生存したまま待つ場合にも介入しません。再開によって権限、作業範囲、安全装置、レビュー基準、デバッグ上限を拡大しない方針です。これらすべての停止経路を現在版の実機で確かめたわけではありません。(検証ステータス: 一部検証 / V12)

2026-09-06 の旧版の Mac 上では、会話整理の検知記録を受けて再起動せず終了する経路を確認しました。検知と状態判定の根幹は現在と対応しますが、その後に監督処理の変更があります。検知記録を書けない場合は条件次第で再起動する余地があり、会話整理だけでは停止を保証しません。確実に止めるための操作は、監督プロセスへ中断のシグナルを送ることです。(検証ステータス: 一部検証 / V12)

## 学習記録(LESSONS)と改善の承認

経験を別の案件で誤用しないよう、LESSONS は共通の教訓と案件固有の知識に分け、関連する記録を選んで参照します。秘密の値は保存しません。判断の優先順位は、現行の手順、承認済みの改善スキル、LESSONS、過去の記録の順です。2026-10-09 の基盤改善には、承認した教訓を既存手順へ反映し、保留する候補を分けた記録があります。範囲は当時の改善作業で、新規スキルの保存実績を示しません。(検証ステータス: 実機検証済み / V20)

改善候補は正本の記録から集計し、繰り返し成功した経験だけでなく失敗例や既存手順との重複も検討します。草案の全文を示して人の承認を得るまで保存しません。2026-10-09 の当時版では、承認を待って既存手順へ反映する経路を確認していますが、後から変わった手順や入力全体の再確認ではありません。(検証ステータス: 実機検証済み / V20)
