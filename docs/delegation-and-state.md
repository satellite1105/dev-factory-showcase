# 委譲と状態管理

> 記述時点: 2026-10。内容は非公開の内部概要資料(v2 系)から概念レベルで書き下ろしたもので、内部仕様は今後変わる可能性があります。

## Codex-first の方針

Claude は判断や設計、統合、レビューを担当し、実装とデバッグは最初に Codex へ渡します。多数のファイルの精読、広い範囲の検索、大量の集計や照合、データ変換、処理用スクリプトの作成なども委譲の対象です。Claude が扱える仕事でも、この分担によって使用量を抑える方針です。検証の根拠となる実装の委譲例は小規模な開発であり、作業全種類や削減効果を測ったものではありません。(検証ステータス: 実機検証済み / V02)

## 委譲の単位と渡す情報

委譲は担当ファイルが明確なタスクに分けます。同時に走るタスク同士の担当を重ねず、共通の型や接続仕様が必要なら、それを先に確定するタスクを設けます。複数の委譲をまとめて出す際も、各担当にタスクの識別情報、必要な要件・設計、担当ファイル、テスト方法、報告形式を渡します。並列実装の運用例はありますが、速度の比較測定はありません。(検証ステータス: 実機検証済み / V05)

操作する案件の境界を伝え、担当外のファイル、別の案件、基盤の設定を変更しないように指定します。ただし、この指定は指示文によるもので、Codex 側の範囲外書き込みを技術的に封じるものではありません。共有領域を指す委譲について承認が必要になることは確認されていますが、範囲の限定全体は一部の検証に留まります。(検証ステータス: 一部検証 / V17)

基盤の共有領域への書き込みには、Claude が直接操作する場合も Codex へ渡す場合も承認の境界を設けています。この境界の検査は確認済みですが、ハードリンク経由の書き込みには未解決の限界があります。(検証ステータス: 実機検証済み / V15)

削除や本番の変更、外部公開、大きな課金、秘密情報の出力など、人の確認が必要な操作は自動進行の対象から外します。利用者が個別に確認を求めた操作も同様です。危険操作への対応は一部確認されていますが、すべての操作種類を網羅した検証はありません。(検証ステータス: 一部検証 / V19)

別途、許可する作業範囲・期限・回数を利用者が先に確認し、本人認証で確定した範囲だけを追加確認なしで進める承認方式を設計しています。一連の動作は実機で未検証であり、ここでは内部の構成や設定値を扱いません。(検証ステータス: 設計済み(未検証) / V18)

## 事前チェックで止めない

Codex への事前の動作確認を、全タスクを始めるための必須の関門にはしません。確認だけの失敗から、実際には委譲できる仕事まで Claude へ移すことを避けるためです。まず対象タスクを委譲し、その結果を見て対応する方針です。検証記録は実装を渡した経路についてのもので、事前確認の有無を比較した試験ではありません。(検証ステータス: 実機検証済み / V02)

## 失敗の分類とタスク単位のフォールバック

呼び出しのエラー、応答が空、時間切れ、認証や準備の問題などはインフラ系の失敗とします。一方、Codex が使えていても報告形式が不十分、テストが未実行、失敗したテストが残る場合は通常の失敗として分けます。いずれも、そのタスクまたはデバッグのラウンドだけを、条件を変えず Claude の coder または debugger に渡します。通常の失敗が起きても、次の独立したタスクでは再び Codex から始めます。タスク単位のフォールバックには実運用の記録がありますが、故障を意図的に起こした網羅試験ではありません。(検証ステータス: 実機検証済み / V03)

引き継ぐ際は既存の変更を保持し、リーダーがテストで到達点を確認して伝えます。時間切れの応答後も元の作業が続く可能性があるため、同じファイルへの二重の書き込みに注意します。実際に作業したのが Codex か Claude か、切り替えた理由は何かを、タスク表と状態の記録に残します。(検証ステータス: 実機検証済み / V03)

## circuit breaker

実装とデバッグのフェーズでは、それぞれ別にインフラ系の連続失敗を数えます。成功または通常の失敗が入れば連続数を戻し、インフラ系が2回続いたら、そのフェーズの残りは Claude が担当します。発動した時点と理由を記録し、別フェーズでは数え直します。実際の発動例はありますが、多数の発動例に基づく評価ではありません。(検証ステータス: 実機検証済み / V04)

## 難易度による事前分類

リーダーは Codex へ渡す前に作業の難しさを区分し、それに応じたモデルを明示する設計です。迷う場合は標準の区分を選びます。Codex が自分でモデルを選んだり、自動で上位へ切り替えたりする運用にはしていません。この分類の妥当性と効果を確かめた記録はありません。(検証ステータス: 設計済み(未検証) / V22)

## PROJECT_STATE

PROJECT_STATE は、会話を離れても案件の進行を把握できるようにする状態の記録です。案件名・状態・更新日時、改変しない依頼原文、承認を得た変更、GOAL_CONTRACT、工程の進捗、現在の問題と対応、デバッグとレビューの試行状況、実行者と切り替え理由、検証結果と残課題、次の作業を収めます。必要に応じて学習記録や、自動再開に使う実行識別情報・チェックポイント・停止理由も残します。これを使う手動再開は設計されており、再開の検証記録は確認されていません。(検証ステータス: 設計済み(未検証) / V10)

以下は架空の案件 `sample-project` の説明用の再構成です。値はすべて架空で、実行や検証の証拠には使いません。項目を抜粋しています。

```markdown
# PROJECT_STATE: sample-project
案件: sample-project
status: in_progress
最終更新: 架空の作業日

## 依頼原文
短い文章の単語を数える道具を作る。
## 承認済みの変更
なし。
## GOAL_CONTRACT
objective: 単語数を表示できる道具
done_when: 合意した入力例で期待値と一致する
verification: 設計に記載したテストを実行する
constraints: 外部への送信を行わない
allowed_files: sample-project の実装とテスト
budget: 既存のやり直し上限に従う
blocked_stop_condition: 上限内で解決できず判断が必要
last_verified_evidence: 未検証
## 進捗・現在の状態
設計済み。実装中。不具合の報告なし。デバッグ・レビューは未着手。
## 実行者
担当タスクを Codex が実装中。フォールバックなし。
## 検証結果
未実行。スコア未確定。完了条件は未確認。
## 再開手順
実装タスクの結果を確認し、設計に記載したテストを実行する。
```

## GOAL_CONTRACT と completion gate

GOAL_CONTRACT は、既存の要件や設計を参照しながら完了の意味を固定する欄です。`objective` は目指す状態、`done_when` は確かめられる達成条件、`verification` は検証手段、`constraints` は守る制約、`allowed_files` は変更範囲、`budget` は既存のやり直し上限への参照、`blocked_stop_condition` は人の判断へ止める条件、`last_verified_evidence` は最後に独立して確認した証拠を表します。範囲の記述自体に技術的な強制力はなく、未確認の証拠は未検証と明記します。(検証ステータス: 設計済み(未検証) / V11)

planner が目的・完了条件・制約の材料を作り、architect が検証方法や範囲、上限、停止条件を具体化します。リーダーが状態記録へ集約し、reviewer が対象版と証拠を照合します。同じエラーが続いたときに方法を変える規則は試行の戦略であり、それ自体を停止条件にはしません。(検証ステータス: 設計済み(未検証) / V11)

completion gate は、完了条件を満たし、検証に成功し、対象版に対応する最新の証拠があり、レビューに合格し、重大な制約違反も停止条件への該当もないことを求めます。どれかが欠ければ `completed` とせず、`blocked` として最良の成果、最終スコア、未達事項、必要な判断を残す設計です。報告済みであることだけでは完了になりません。この判定経路の実案件での検証記録はありません。(検証ステータス: 設計済み(未検証) / V11)

## 中断からの再開

再開時は `in_progress` の案件について、最後に進めた工程の成果と状態記録を読み、続きから担当を割り当てる設計です。完了済みタスクは繰り返さず、実行者と circuit breaker の状態を引き継ぎます。同じフェーズで発動済みなら残りを Claude が担当します。古い記録に GOAL_CONTRACT がなくても既存の要件・設計から補います。手動の中断・再開について、実機の検証記録は確認されていません。(検証ステータス: 設計済み(未検証) / V10)

## 監督付き自動再開

無人で進める長い実行では、任意の監督プロセスが子プロセスの終了を見守る設計です。実行中だけ動き、常駐はしません。異常終了に加え、状態を読めること、`in_progress` であること、実行識別情報とチェックポイントの一致、想定外の変更や承認待ちがないことなどをすべて満たした場合だけ再起動します。同じチェックポイントで最大2回とし、まず同じセッション、次に状態記録を使う新しいセッションを試します。異常終了からの自動再起動そのものは検証記録がありません。(検証ステータス: 一部検証 / V12)

再起動しない条件には、正常終了、利用者による中断や終了シグナル、利用者の判断待ち、`blocked` または `completed`、状態の不明・破損、予想外の作業ツリーの変化、Codex がまだ作業中または状態不明、ループの検知があります。利用制限による一時停止には介入しません。再起動を行う場合も、権限、安全装置、レビュー基準、デバッグの上限、作業範囲を拡大しない方針です。(検証ステータス: 一部検証 / V12)

検証済みなのは、セッションをクリアした記録を検知し、再起動を行わない通常の経路です。クリアの検知記録を書けなかった場合まで停止を保証するものではなく、条件次第で再起動する余地が残ります。確実に止める必要がある場合は、監督プロセスへ中断のシグナルを送ります。(検証ステータス: 一部検証 / V12)

## 学習記録(LESSONS)と self-improve

LESSONS には、複数の案件で使える経験と、その案件固有の知識を分けて残し、重複を避けます。参照は関連する記録や直近の記録に絞り、秘密の値は保存しません。判断の優先順位は、現行の手順、承認を得た改善スキル、LESSONS、過去の記録の順です。学習記録から改善候補を扱う流れには検証記録があります。(検証ステータス: 実機検証済み / V20)

self-improve は、繰り返し成功した経験を候補として抽出し、失敗例や既存の手順との重複も検討して草案にまとめ、利用者の承認を得て反映する流れです。少数の経験だけで一般化せず、候補の集計には正本の記録を使います。全文を確認できる形で提示し、承認前には保存しません。承認待ちで止まり、未承認の保存をしない関門は検証済みです。ただし、確認されている反映は既存手順への改善で、新しい改善スキルの保存実績はありません。(検証ステータス: 実機検証済み / V20)
