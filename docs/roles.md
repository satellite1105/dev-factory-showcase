# 役割と分担

> 記述時点: 2026-10。内容は非公開の内部概要資料(v2 系)から概念レベルで書き下ろしたもので、内部仕様は今後変わる可能性があります。

## 分担の考え方

Claude は開発の方針を決め、成果をまとめ、依頼に沿っているかを判断します。Codex はコードの作成や修正に加え、大量の資料を扱う調査やデータ処理を受け持ちます。実装を Codex に渡して進める経路は、小規模な開発で確認されています。ここで示す役割分担の全項目を個別に検証したという意味ではありません。(検証ステータス: 実機検証済み / V02)

以下の5役は planner(企画)、architect(設計)、coder(実装)、debugger(デバッグ)、reviewer(検証)です。これらをリーダー(オーケストレーター)がつなぎ、成果物を次の工程へ渡します。企画から納品まで進めた小規模な確認例があり、大規模な案件での完走率を示すものではありません。(検証ステータス: 実機検証済み / V01)

## リーダー

**責務:** 工程の進行、仕事の割り振り、成果の統合、最終判断と報告を担います。工程が変わる際には案件の状態を記録し、担当者の成功報告を受けても自分の環境でテストを実行して確認します。**入力:** 利用者の依頼と各役の成果・検証の証拠です。**出力:** 統合した成果物、進捗の記録、利用者への報告です。**やらないこと:** 大きな実装を自分で抱えること。直接のコード修正は、読み込み指定の調整など小さな統合作業に限ります。未実行や省略されたテストを成功として扱いません。(検証ステータス: 実機検証済み / V01)

## planner

**責務:** 依頼を、作るものと確かめ方が分かる要件へ整理します。曖昧な点は仮定として明示し、初版に必要な機能と後で検討する機能を分けます。**入力:** 利用者が書いた依頼そのものです。**出力:** 目的、利用場面、識別番号を付けた機能要件と成功条件、非機能要件、仮定、対象外の範囲をまとめた要件定義です。**やらないこと:** 設計や実装に踏み込むこと、依頼の一部を無断で取り除くこと。除外したい内容は未承認の提案として残し、承認までは要件を維持します。(検証ステータス: 実機検証済み / V01)

## architect

**責務:** 要件を、実装と検証に着手できる設計へ変換します。採用実績、依存の少なさ、テストのしやすさを考慮して技術を選びます。**入力:** planner が整理した要件です。**出力:** 選定理由、構成、接続部分の取り決め、テスト方針と実行方法、担当を割り当てたタスク表です。**やらないこと:** 設計担当として製品の実装まで進めること。(検証ステータス: 実機検証済み / V01)

同時に進めるタスクでは、編集するファイルが互いに重ならないようにします。共通の型や接続部分は先行するタスクで定め、その成果を使って残りを並列に進めます。この分け方による実装の運用例はありますが、速度向上の定量比較は行っていません。(検証ステータス: 実機検証済み / V05)

完了条件のうち、検証手段、編集可能な範囲、制約、既存のやり直し上限、判断を求めて止まる条件も設計で具体化します。リーダーが GOAL_CONTRACT にまとめ、reviewer が成果と照合する構想です。この完了判定の仕組みは、実案件での判定記録が確認されていません。(検証ステータス: 設計済み(未検証) / V11)

## coder

**責務:** 割り当てられたタスクを実装し、テストによって結果を示します。まず Codex に委ね、利用できない場合や失敗した場合に、Claude の coder がそのタスクを引き継ぎます。**入力:** 担当ファイル、接続部分の取り決め、検証方法が明記されたタスクです。**出力:** コード、テスト、変更ファイルと実際のテスト結果を含む報告です。**やらないこと:** 担当外への変更、独断での接続仕様の変更、依頼されていない機能の追加、未実行のテストを成功とする報告。担当外の問題は報告に残します。タスク単位での引き継ぎは実運用で確認されています。(検証ステータス: 実機検証済み / V03)

実装では先にテストを用意し、成功を確認するまで完了としない方針です。同じエラーで2回失敗した場合は、次の試行で方法を変えます。この試行方針自体の検証記録は確認されていません。(検証ステータス: 設計済み(未検証) / V23)

## debugger

**責務:** 不具合を再現し、仮説を証拠で確かめ、原因に絞った修正を行います。Codex によるデバッグが利用不能または失敗となった際は、Claude の debugger へ該当ラウンドを引き継ぐ方針です。**入力:** 失敗したテスト、エラー、再現方法、または reviewer の指摘です。**出力:** 解決・再現不能・未解決の別、原因、修正内容、全テストの結果、各指摘に対する修正前後の確認です。**やらないこと:** 不具合と関係のない整理、外観の変更、機能の追加。フォールバックの検証根拠はタスク単位の運用例であり、デバッグの全経路を網羅した試験ではありません。(検証ステータス: 実機検証済み / V03)

修正後は全テストで副作用を調べます。同じ方針で2回失敗したら仮説を変え、デバッグは最大3ラウンドまでとします。解決できなければ調査結果と残る仮説を報告する設計で、この上限に至る動作の検証記録はありません。(検証ステータス: 設計済み(未検証) / V23)

## reviewer

**責務:** 実装側から独立して、依頼と成果の一致を確かめ、根拠を添えて採点します。要件定義に抜けがあれば、元の依頼と利用者が承認した変更を優先して指摘します。**入力:** 依頼、承認済みの変更、完了条件、要件・設計・タスク、成果物の対象版、テスト方法です。**出力:** 総合点と合否、評価項目ごとの点と根拠、問題点、修正指示、重大な誤りを構造化した JSON です。**やらないこと:** 製品コードの修正、実装側の自己申告だけでの合格、依頼に必要のない過剰な検証の要求。採点と合否判定の運用例はありますが、採点の再現性は保証されません。(検証ステータス: 実機検証済み / V06)

確認方法は成果物に合わせます。外観の要求には描画結果の観察を使い、環境上確認できない点は欠陥と分けて証拠不足として記録します。ただし、完了条件の確認が欠けた状態を合格にはしません。(検証ステータス: 実機検証済み / V06)

## 役割ごとのモデルの割り当て

Claude のモデルは役割に合わせて明示します。リーダー、architect、reviewer には判断力を重視した上位の系統を、planner、事実確認役、フォールバック時の coder と debugger には中位の系統を割り当てる考え方です。指定を省いた際の意図しない継承を避けます。上位の役割と planner の実モデルを確認した記録はありますが、中位の一部の役割は更新後の確認が残っています。(検証ステータス: 実機検証済み / V21)

Codex のモデルも委譲前にリーダーが難易度を見て指定する設計です。選択の考え方と未検証の範囲は、[委譲と状態管理](delegation-and-state.md)で説明します。(検証ステータス: 設計済み(未検証) / V22)

## Claude 使用量を抑える考え方

実装・デバッグだけでなく、多数のファイルの読み込み、広範囲の検索、集計、照合、データの整形、数値の再計算も Codex-first の対象です。調査という名目でも、処理量が大きい仕事は Codex へ渡します。Claude は結果の要点と証拠を受け取り、設計判断、統合、レビューへ集中します。実装の委譲は確認済みですが、この方針全体の使用量削減を定量的に示す資料はありません。(検証ステータス: 実機検証済み / V02)
